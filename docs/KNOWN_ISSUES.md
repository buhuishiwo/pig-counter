# KNOWN_ISSUES — 已知问题

> 最后更新：2026-11-18｜以下均为**功能层**已知限制，不含运维待办

## OCR 已知限制（后续优化，低优先级）

### OCR 后端不可达时，单张识别会卡约 600 秒（2026-11-18 现场发现）

v3.1 的水印识别流程是"原样输出全文 1 次 → 4 个字段各最多问 2 次 → JSON 兜底 1 次"，**最坏 10 次请求**，
每次 `httpx.AsyncClient(timeout=60.0)`。若 OCR 后端端口被防火墙/安全组 **DROP**，每次都要等满 60 秒超时。

- **影响**：单张 ≈ 600 秒，批量（5 并发）同样被拖死；浏览器/隧道通常 60~100 秒就放弃（nginx 日志表现为 `499`）
- **附加风险**：记录在调 OCR **之前**已写库，用户反复重试会产生重复记录
- **判据**：`ping <host>` 通但 `curl http://<host>:<port>/v1/models` **超时**（而不是 `Connection refused`）= 端口被白名单/安全组挡住
- **缓解（已用）**：把 `OCR_API_KEY` 置空——`watermark_ocr.py` 首行 `if not OCR_API_KEY: return None`，一次请求都不发，单张恢复 2~5 秒；代价是不再写 `watermark_data`（单元/栏号仍可从文件名兜底）
- **后续方向**：`_call_ocr` 超时降到 5~10 秒 + 连续失败即熔断本轮剩余图片

### qwen-vl-ocr 分辨率上限

qwen-vl-ocr 视觉 token 限制约 1280 个，对应约 900×900 像素。高分辨率原图（如 1706×1279）中的细小文字会被压缩后模糊，导致无法识别。

- **影响**: 部分高分辨率图片的墙面标记可能读不出来
- **缓解**: 当前实现会返回 null，走人工录入
- **后续方向**: 可考虑上传前在前端压缩图片到合理尺寸，或切片识别

### 低对比度墙面标记

部分养殖场墙面标记（粉笔字、刻划数字）与背景对比度极低，qwen-vl-ocr（当前唯一 OCR 链路，旧 PaddleOCR 已废弃）也无法识别。

- **样本**: 19号栏舍部分图片
- **影响**: 这类图片 OCR 返回 null，需人工录入
- **后续方向**: 图像预处理增强（CLAHE、锐化），或引导用户拍照时靠近标记/补光

### 个别图片整段水印读不出（已缓解，未根除）

极少数图片在"原样输出"模式下，qwen-vl-ocr 只返回文字坐标、不返回文字内容。

- **影响**: 这批图的栋舍/承储单位可能取不到（栏号可用文件名兜底）
- **已做**: 对缺失字段"定向补问"（"读出「所在栋舍」后面的文字"），单字段最多问 2 次；实测 `新新标准` 39 张已全部补齐
- **仍未解**: 若整张图连单字段提问也读不出，只能人工补或换 `qwen-vl-max`

## 批量上传（分批）已知限制

> 分批机制：前端每 50 张一批调用 `/api/batch/upload`，跨批合并后展示。

### 同一栏的照片跨批时会重复入库（已修复 2026-11-17）

同一 (单元, 栏号) 的多张照片落在不同批次时，每批各写一条 `detection_records`，
界面合并成一行但统计页会重复计数。

- **已修**: 合并后调用 `POST /api/batch/dedupe` 删除被淘汰的重复记录
  （仅限最近 1 天内、由本批次产生），实测库内记录数与界面栏数一致，见 `DEPLOYMENT_LOG` #163
- **注意**: 若在识别过程中刷新/关页导致批次未走完，可能残留少量重复记录，可手动清理

### 单批彻底失败后只能整轮重跑（不能续跑）

**先解释"一批"是什么**：分批上传时，前端把文件按 **50 张一批**切分，逐批调用
`/api/batch/upload`。例如 500 张 = 10 批，504 张 = 11 批（前 10 批各 50 张、最后一批 4 张）。
单批耗时实测约 **100~115 秒**。

**什么是"彻底失败"**：每批最多尝试 **2 次**（间隔 1.2 秒）。以下情况会两次都失败：

| 原因 | 说明 |
|:--|:--|
| 网络中断 / 断网 | 上传或等响应时连接断开 |
| 响应被截断 | 实测遇到过：前端报 `Unexpected end of JSON input`，重试后仍截断 |
| 服务端 5xx | 容器重启、OOM、进程被杀等 |
| 4xx（参数/体积） | 不重试，直接失败（重试也没意义） |

**失败后用户会看到什么**：

1. 右上角通知卡（error，6 秒后自动消失）：
   **批量检测失败 / 识别过程异常，请重新尝试**
   （技术细节只写进系统日志，如"第 7/11 批响应不完整"，不展示给用户）
2. **界面回到"已选文件夹、未识别"状态**：结果被清空，可再次点击「开始识别」
3. **本次已写入的记录会被回滚**（调用 `/api/batch/dedupe` 删除本次产生的 record_id，
   仅限最近 1 天内），避免留下界面上看不到的脏数据
   - 若失败原因就是"后端不可用"，回滚请求也发不出去 → 记录会进入
     `localStorage` 的待回滚队列（`pigcount_pending_rollback`），
     下次打开页面或开始识别时自动补做（实测：后端恢复后刷新页面，12 条残留被自动清掉）

> 区分：**用户主动取消**时行为不同 —— 已完成部分仍然保留并展示，
> 提示"已取消：完成 N/M 批，结果仅含已完成部分"。

**为什么不自动跳过失败批次继续跑**：跳过后仍能生成报表，但报表会**静默缺少一部分栏**
（同一个单元的合计、差值都不完整），比直接报错更容易误导，所以现在的策略是
"停下来让人知道"。

**重跑怎么做**：

1. 点「开始识别」重新上传整个文件夹（当前没有"从第 N 批继续"）
2. 由于失败时已回滚本次写入的记录，重跑不会产生重复
3. 仍有一种残留可能：服务端已写入、但响应在回传时丢失，且前端连"这次成功了几批"都没收到 ——
   此时回滚列表可能不完整，需按 `image_name` 前缀 + 时间范围人工核对

**规避建议**：

- 用稳定网络，识别过程中**不要刷新/关闭页面**（刷新会触发取消令牌，服务端会停下）
- 超大目录（>300 张）可先按子目录分开跑，减少单轮时长和失败面
- 失败后先看日志里的"第 X/Y 批失败 + 原因"，再决定重跑还是换网络环境

**后续方向**（未实现）：

- 「从第 N 批继续」：前端保留已完成批的 `units` 与剩余文件切片，失败后只补跑剩余批
- 批次幂等：后端用 `batch_token` + 文件指纹去重，重跑时跳过已处理的图片

### 老格式水印不再适配

`35栏26头`、`13栋35栏` 一类历史写法不再解析单元/栏号（现按"标签: 值"取字段）。

- **影响**: 这类历史照片会以文件名为栏号、单元记为「未识别单元」，各占一行（不会互相合并）
- **约定**: 甲方已统一为新格式，历史数据按"能跑、不丢行"处理
