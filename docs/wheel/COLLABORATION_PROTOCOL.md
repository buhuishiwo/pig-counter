# 人机协作协议 (Collaboration Protocol)

**版本**: V2.2
**定位**: 定义用户与 AI Agent 之间的协作规则、流程与文档治理约定。本协议的核心概念和格式规范可跨项目复用。
**出处**: 从温州粮食数据中台项目（data_platform）实战中抽象，经猪识别项目（PigCount）验证修正。

---

## 1. 核心模型：三大件 + Feedback Loop

```
  ┌──────────────────┐  ┌──────────────────┐  ┌──────────────────┐
  │    TODO_LIST     │  │   DEPLOY_LOG     │  │    HANDOVER      │
  │  记录：下一步做什么？ │  │  记录：做了哪些事？ │  │  记录：现在是什么   │
  │                  │  │  踩过什么坑？      │  │  状态？           │
  │  · 按 P1/P2 排    │  │  · 交付 + 条目   │  │  · 30 秒快照      │
  │  · 每项带验收标准  │  │  · 发现→方案→实施  │  │  · 环境速查表      │
  │  · 无已完成项堆积  │  │  · 只追加不删改    │  │  · 关键路径图      │
  │  · 技术债独立      │  │  · 可搜索回查      │  │  · 历史按日追加    │
  └────────┬─────────┘  └────────┬─────────┘  └────────┬─────────┘
           │                     │                     │
           └─────────────────────┼─────────────────────┘
                                 │
                     ┌───────────┴───────────┐
                     │     Feedback Loop     │
                     │                       │
                     │  读 HANDOVER → 取任务  │
                     │  执行 → 看结果         │
                     │  成功更新 / 踩坑记录    │
                     │  session 末 → 收尾仪式  │
                     └───────────────────────┘
```

**三者关系**：

```
新 session 启动 → 读 HANDOVER（恢复上下文）→ 读 TODO_LIST（取任务）
执行中踩坑    → 写 DEPLOYMENT_LOG（记录方案，可回查）
session 结束  → 刷新 HANDOVER 顶部框 + 更新 TODO_LIST 勾选
```

## 2. 滚动迭代飞轮 (Flywheel)

### 2.1 一句话

**每一次 session 的输出（更新后的三大件），就是下一次 session 的输入。**

### 2.2 飞轮全景

```
 ┌──────────────────────────────────────────────────────┐
 │                                                      │
 │   新 session 开始                                     │
 │       │                                              │
 │       ▼                                              │
 │   ┌─────────────────────┐                            │
 │   │ 读 HANDOVER 顶部框   │   ← 30 秒恢复上下文        │
 │   │ 读 TODO_LIST 取 P1   │   ← 知道下一步干什么       │
 │   └─────────┬───────────┘                            │
 │             │                                        │
 │             ▼                                        │
 │   ┌─────────────────────┐                            │
 │   │ 执行 P1 任务         │                            │
 │   └─────────┬───────────┘                            │
 │             │                                        │
 │        ┌────┴────┐                                   │
 │        ▼         ▼                                   │
 │     成功        失败                                  │
 │       │          │                                   │
 │       │     ┌────┴────┐                              │
 │       │     ▼         ▼                              │
 │       │   能修       修不通                            │
 │       │     │          │                             │
 │       │     ▼          ▼                             │
 │       │   修→重试   追加 DEPLOY_LOG 条目(🛑)         │
 │       │     │          │                             │
 │       └─────┴──────────┘                             │
 │              │                                       │
 │              ▼                                       │
 │   ┌─────────────────────┐                            │
 │   │ session 收尾仪式（2分钟）                          │
 │   │                     │                            │
 │   │  ① 阶段全貌         │  → 刷新 HANDOVER 30 秒快照   │
 │   │  ② 下次从哪里上手    │  → 更新 TODO_LIST 勾选      │
 │   │  ③ 历史回溯兜底      │  → 追加 DEPLOY_LOG 条目     │
 │   └─────────┬───────────┘                            │
 │             │                                        │
 │             ▼                                        │
 │   session 结束 → 下次启动时 HANDOVER 已是最新状态       │
 │                                                      │
 └──────────────────────────────────────────────────────┘
```

### 2.3 飞轮为什么会加速

| 轮次 | 状态恢复成本 | 实际推进占比 |
|:-----|:------------|:------------|
| 第 1 次 | 读 HANDOVER（30 秒） | ~90% |
| 第 2 次 | 读 HANDOVER（30 秒），上次的坑已标注 | ~90% |
| 第 N 次 | TODO 优先级越来越准，DEPLOY_LOG 可搜索 | ~95% |

**关键**：上下文恢复成本不随项目复杂度增长。"知道该做什么"O(1)，"知道踩过什么坑"O(1)。时间花在推进上，不是花在回忆上。

### 2.4 飞轮怎么卡死的

```
跳过收尾仪式
    ↓
HANDOVER 顶部框过期
    ↓
下次 session 上来翻记录找状态
    ↓
花 20 分钟恢复上下文，没时间推进
    ↓
更不想花时间写文档
    ↓
飞轮卡死 → 每次 session 从零开始
```

**唯一的硬规则**：每次 session 结束前，花 2 分钟刷新 HANDOVER 顶部框。跳过一次就破功。

## 3. 飞轮组件定义与格式规范

### 3.1 TODO_LIST — 待办清单

**定义**：记录下一步做什么。每次 session 开始读，任务完成或新增时更新。

**模板**：

```
# 待办任务清单 (TODO List) — <项目名>

**最后更新**: YYYY-MM-DD HH:MM
**状态**: 一句话 + 徽标（如 🟢 阶段名 — 一句话概况）

---

## 1. 总体进度
| 阶段 | 里程碑 | 状态 | 进度 |
|:-----|:-------|:-----|:-----|
| P0 xxx | ... | ✅ 已完成 | 100% |
| P1 xxx | ... | 🟢 进行中 | 80% |
| P2 xxx | ... | ⬜ 待执行 | 0% |

## 2. <当前阶段> — 当前重点
（按子任务组嵌套子节，每个子节可独立验收）

### P1.1 子阶段名

- [ ] **Task N — 标题**
  验收：可验证的一句话（包含具体检查条件）

## 3. 技术债务
（不阻塞当前但值得记录的问题，与待办池分离）
| 项 | 说明 | 优先级 |
|:---|:-----|:-------|

## 4. 任务依赖图
（ASCII 依赖图，标注：`← 依赖` / `独立，可并行` / `阻塞：原因`）

## 5. 历史完成记录
（已完成任务移入此处，按阶段分组，不删除）
```

**字段规则**：

| 字段 | 规则 |
|:-----|:-----|
| 优先级 | P1=阻塞生产/下周必动, P2=本月可做, P3=锦上添花 |
| 验收标准 | 可验证的一句话，判断"做完"的充要条件。必须包含具体检查方式（命令、行为、数值） |
| 状态徽标 | ✅ 已完成 / 🟢 进行中 / 🟡 待验证 / ⬜ 待执行 |
| 子任务嵌套 | 当前阶段下可用 `### P1.1 xxx` 嵌套子节，每个子节有独立的 Task 列表和验收 |

**验收标准正反对比**：

反面 ❌：
```
- [ ] 优化性能
- [ ] 修 bug
- [ ] 识别准确率可接受
```

正面 ✅：
```
- [ ] **Task 1 — 修复 CSV 导出损坏**
  验收：MySQL LOAD DATA 成功，行数 > 0
- [ ] **Task 2 — OCR 大规模验证**
  验收：478 张图测试通过，准确率 >= 90%，误检率 <= 5%
```

### 3.2 DEPLOYMENT_LOG — 部署日志

**定义**：记录做了哪些事、踩过什么坑。交付或踩坑时追加，不回溯修改旧条目。

**模板**：

```
# <项目名>部署实施日志 (Deployment Log)

**文档说明**: 一句话说明本文档用途
**当前状态**: <阶段> — <一句话>
**最后更新**: YYYY-MM-DD HH:MM

---

## 1. 环境信息 (Environment Context)
（部署环境 / OS / 网络 / 节点 / 端口 / 关键配置，一次性写入，低频率更新）

* **本地开发环境**: ...
* **远程生产环境**: ...
* **关键配置**: ...（容易踩坑的配置项）

## 2. 实施进度追踪 (Progress Tracker)

### 阶段一：xxx

- [X] **1.1 子阶段名**
  - [X] 具体任务 A
  - [X] 具体任务 B
- [ ] **1.2 子阶段名**
  - [ ] 具体任务 C

### 阶段二：xxx

- [X] ...

## 3. 实施记录 (Implementation Log)

| 编号 | 日期 | 标题 | 说明 | 状态 |
|:-----|:-----|:-----|:-----|:-----|
| 1    | ...  | 部署 Grafana 看板 | 部署到 Node3，对接 Prometheus，systemd 自启，访问 :3000 | ✅ 已交付 |
| 2    | ...  | 修复 DS API 50014 | **发现**: processDefinitionCode 不在 body 而在 URL query。**方案**: 改用 query param 传递。**实施**: fix_ds_api_server.sh 部署到 Node1 | ✅ 已修复 |
```

**字段规则**：

| 字段 | 规则 |
|:-----|:-----|
| 编号 | 整数自增，从 1 起，不重用 |
| 日期 | 实施日期 YYYY-MM-DD |
| 标题 | 简洁描述事件，优先动词开头（`部署 xxx` / `修复 xxx`），名词短语也可接受（`DS 管道与 cron 双重维护`） |
| 说明 | **交付条目**：做了什么 + 结果。**踩坑条目**：三段式 **发现** → **方案** → **实施**。可夹带关键命令/报错 |
| 状态 | 见下方状态徽标表 |

**状态徽标**：

| 徽标 | 含义 | 使用场景 |
|:-----|:-----|:---------|
| ✅ 已交付 | 功能/配置完成 | 新功能上线、配置变更 |
| ✅ 已修复 | Bug 修复 | 问题定位并修复 |
| ✅ 已解决 | 问题解决 | 环境/依赖/兼容性问题 |
| ✅ 已验证 | 验证通过 | 测试/冒烟/回归验证 |
| ✅ 已确认 | 决策确认 | 方案评审、策略调整 |
| 🟡 待完成 | 部分完成 | 有明确下一步 |
| 🟡 待验证 | 已实施待验证 | 等明天/下次触发 |
| ⬜ 待执行 | 计划中 | 已知待办 |
| 🛑 阻塞 | 被阻塞 | 外部依赖或无法解决 |
| ℹ️ 已知 | 知晓但不处理 | 已知限制、策略决策 |

**说明列三段式适用范围**：

| 条目类型 | 说明格式 | 示例 |
|:---------|:---------|:-----|
| 踩坑/问题修复 | 三段式：**发现**→**方案**→**实施** | **发现**: MySQL 容器默认 UTC。**方案**: 添加 TZ=Asia/Shanghai。 |
| 功能交付 | 简述：做了什么 + 结果 | 部署 Grafana 10.4.3 到 Node3，5 面板看板创建完成 |
| 决策记录 | 简述：决策内容 + 理由 | DS 保留为可视化触发器，缩为 1 节点调 daily_etl.sh |
| 验证记录 | 简述：验证项 + 结果 | API 3 端点 200 OK，ADS 6 表数据一致 |

**规则**：
- 只追加不删改。需更新状态时追加新条目引用旧编号（如 `关联 #125`）
- §2 进度追踪是 §3 实施记录的粗粒度快照，两者不重复书写细节
- §1 环境信息一次性写入，仅在架构变更时更新

**反面案例** ❌：

```
| 5 | 修好了 | 改了个配置 |
```
→ 无日期、标题看不出做了什么、说明无法复用。下次遇到同样的问题不知道怎么修。

```
| 6 | 2026-06-01 | 更新了东西 | 做了一些修改 | ✅ 已完成 |
```
→ 标题不具体、说明无内容。正确写法见上方正面示例。

### 3.3 HANDOVER_CONTEXT — 交接上下文

**定义**：记录当前项目是什么状态。每次 session 结束时刷新顶部框 + 底部追加历史摘要。

**模板**：

```
# 交接上下文 (Handover Context) — <项目名>

---

## 30 秒快照

| 项 | 内容 |
|:---|:-----|
| **项目概要** | 一句话，含技术栈 + 数据流 + 关键指标 |
| **当前阶段** | P 编号 + 阶段名 + 进度 |
| **最新变更** | 本次 session 最重要的 2-3 件事，不含过程细节 |
| **下次第一件事** | 明确可执行，新接手者不看历史就能动手 |

---

## 环境速查

| 节点 | IP/地址 | 角色 |
|:-----|:--------|:-----|
| Node1 | x.x.x.x | 服务1, 服务2, ... |

**SSH 方式**: （连接说明，如免密登录、ControlMaster、堡垒机跳转等）

**启动/测试速查**:

​```bash
# 后端启动
...

# 前端启动
...

# 健康检查
curl http://localhost:xxxx/...
​```

---

## 关键路径
（ASCII 数据流图，覆盖主要业务流程，架构变更时更新）

---

## 测试数据
（测试文件路径、数据量、结构说明，便于新 session 快速复现）

---

## 历史

### YYYY-MM-DD — 标题
- 要点列表，不写长段落
- 包含关键配置值、端口、PID 等可复现信息
```

**30 秒快照字段规则**：

| 字段 | 要求 | 示例 |
|:-----|:-----|:-----|
| 项目概要 | 一句话，含技术栈 + 数据流 + 关键指标 | `Sqoop → Hive → MySQL → API (<0.1s)` |
| 当前阶段 | P 编号 + 阶段名 | `P4 收尾 — DS 收敛完成，95%` |
| 最新变更 | 2-3 件事，不含调试过程 | `DS 1 节点验证通过；Superset 16/16 修复` |
| 下次第一件事 | 可执行，不看历史能动手。必须含具体操作步骤 | `SSH 到 Node1 执行 ds_simplify.py，然后触发实例验证` |

**"下次第一件事"正反对比**：

反面 ❌：
```
| **下次第一件事** | 继续推进 |
| **下次第一件事** | 根据用户指示继续 |
```
→ 无具体动作，不知道从哪开始。

正面 ✅：
```
| **下次第一件事** | 清理 ESLint 缓存：.gitignore 添加 node_modules/.cache/ → git rm --r --cached → 新 commit → push |
| **下次第一件事** | SSH 到 Node1 执行 ds_simplify.py，然后触发实例验证 |
```

**规则**：
- 顶部框每次 session 结束必须刷新。历史按日期倒序追加，旧条目不动。顶部框过期 = 飞轮卡死。
- 历史条目标题不限动词/名词，但必须简洁可辨识
- 历史条目内容包含关键配置值（端口、PID、路径、命令），便于复现

**反面案例** ❌：

```
### 2026-06-01
- 做了一些修改
- 修复了问题
```
→ 无标题、无具体内容。下次看不知道这天做了什么。

## 4. 文档治理原则

| 文档 | 读时机 | 写时机 | 规则 |
|:-----|:-------|:-------|:-----|
| **TODO_LIST** | session 开始 | 任务完成/新增 | 勾完移入历史，不堆积已完成 |
| **DEPLOYMENT_LOG** | 查历史记录 | 交付/踩坑时 | 只追加条目，不回溯改旧条目 |
| **HANDOVER** | session 开始 | session 结束 | 顶部框 30 秒可读完，底部历史追加 |

---

## 5. Feedback Loop 执行规则

### 5.1 执行流程

```
1. 读 HANDOVER 顶部框 → 恢复上下文
2. 读 TODO_LIST → 取 P1 最优先项
3. 执行任务
4. 看结果：
   ├─ 成功 → 记 DEPLOY_LOG → 更新 TODO → 记 HANDOVER → 下一个
   └─ 失败 → 分析报错 → 尝试修复 → 重试
             修复成功 → 记 DEPLOY_LOG → 继续
             修不通 → 追加 DEPLOY_LOG 条目 🛑 → 挂起，由用户决定下一步
```

### 5.2 收尾仪式（2 分钟）

每次 session 结束前必做三件事，与控制面的飞轮形成闭环：

1. **阶段全貌**     → 刷新 HANDOVER 30 秒快照
2. **下次从哪里上手** → TODO_LIST 勾选
3. **历史回溯兜底**  → DEPLOY_LOG 条目

跳过一次 = 飞轮断链，下次 session 从零恢复。

## 6. 交付自查清单

AI 完成飞轮文档更新后，对照以下清单自查：

### DEPLOYMENT_LOG 自查

- [ ] 新条目编号连续（不跳号、不重用）
- [ ] 标题简洁可辨识（非"做了修改"、"修复了问题"）
- [ ] 踩坑条目含 **发现**→**方案**→**实施** 三段式
- [ ] 交付条目说明含"做了什么 + 结果"
- [ ] 状态徽标准确（已交付/已修复/已解决/已验证/待执行/阻塞）
- [ ] §2 进度追踪与 §3 实施记录一致（进度勾选反映最新条目）

### TODO_LIST 自查

- [ ] **状态** 行反映最新进展（非"继续推进"）
- [ ] 每个 Task 有 `验收：` 标准（非"优化性能"、"准确率可接受"）
- [ ] 已完成任务已移入 §5 历史区，不在 §2 堆积
- [ ] 技术债务独立于待办池（§3 与 §2 分离）

### HANDOVER_CONTEXT 自查

- [ ] 30 秒快照是 4 行表格（项目概要/当前阶段/最新变更/下次第一件事）
- [ ] "下次第一件事"可直接执行（非"继续推进"、"根据指示"）
- [ ] 环境速查含 SSH 连接方式
- [ ] 历史条目有标题 + 要点（非"做了一些修改"）

---

## 7. 跨项目复用

本协议的核心概念和格式规范（§3）是通用的。

### 复用步骤

1. 复制本文件到新项目的 `docs/wheel/COLLABORATION_PROTOCOL.md`
2. 按 §3 模板创建三个空文件（DEPLOYMENT_LOG.md、TODO_LIST.md、HANDOVER_CONTEXT.md）
3. 替换项目特定内容：环境信息、节点表、关键路径图、阶段划分
4. 通用部分不动：章节结构、条目格式、飞轮仪式、治理规则、自查清单

### 最小启动集

- **TODO_LIST**  — 知道下一步做什么
- **HANDOVER**   — 新 session 30 秒恢复上下文
- **DEPLOY_LOG** — 有行为就有记录，从第一次交付开始

协议本身可直接复用。
